# Privacy, legal & store readiness

**This is an engineering input for lawyers, not legal text.** The privacy
policy and terms must be written/reviewed by counsel for the target markets
(e.g. Indonesia UU PDP No. 27/2022, EU GDPR if offered there). Store policies
change often: **re-read Apple's App Review Guidelines / App Privacy details and
Google Play's Developer Policy Center, Data safety and account-deletion pages
right before submission** — the summaries below reflect our understanding at
the time of writing and were not re-verified online for this document.

## 1. Honest data inventory (what the policy must say)

| Data | Purpose | Stored | Encrypted end-to-end? | Who can access on our side |
|---|---|---|---|---|
| Name, email, password hash | account, login | PostgreSQL | No (hash only for password) | operators with DB access |
| Photos (memories, Photo Booth prints) | the core feature | object storage, primary + backup | **Yes** — encrypted on the device (AES-256-GCM); server stores ciphertext only | nobody can view content; operators see size, time, checksum |
| Memory titles, descriptions, dates, **location name/address/coordinates** | memories | PostgreSQL | **No** — readable by the server | operators with DB access |
| Date plans, comments | dates, chat-like comments | PostgreSQL | **No** | operators with DB access |
| Device name, platform, device public key | key sharing, device management | PostgreSQL | public key by nature; not secret | operators |
| Wrapped Couple Key packages, recovery package | photo key distribution / recovery | PostgreSQL | encrypted to devices / to the user's Recovery Key | nobody can unwrap |
| Theme choice and customization | appearance | PostgreSQL | No | operators |
| Subscription status, store transaction ids, amounts | billing | PostgreSQL | No (no card data ever — the stores process payments) | operators with `billing.view` |
| IP address, user id, request route/status/timing | security, abuse prevention, debugging | logs, 30 days | No | operators |
| Crash reports | stability | **not collected yet**; when added: scrubbed stack traces, no content | — | — |

What we must **not** claim:
- "End-to-end encrypted" for the whole app — only **photos** are. Text, dates, locations and comments are not.
- "Even we/the server can never access your photos under any circumstances": because key packages are trust-on-first-use (security.md S8), a compromised server could target a *newly added* device. Safe wording: *"Photos are encrypted on your phone before upload. Our servers store only encrypted copies and do not have the keys to open them."*
- "Military-grade", "unhackable", "100 % secure", "never lost".
- Backups "protect" photos before the backup is verified (the app only shows *Protected* after the backup copy's checksum is verified).

## 2. Policy content checklist

- [ ] Controller identity & contact, DPO/contact email, support channel
- [ ] Data inventory above; legal bases (contract, legitimate interest for security logs, consent where needed)
- [ ] Encryption: photos only, how keys work in plain language, **Recovery Key**: if the user loses every device *and* the Recovery Key and has no partner device to re-share, **photos cannot be recovered by anyone, including us**
- [ ] Backups: two independent storage providers (name them), encrypted DB backups kept 30 days; deleted data persists in backups until they expire
- [ ] Sub-processors: hosting, object storage A & B, monitoring/logging, crash reporting, Apple/Google (payments, push later), e-mail (later)
- [ ] International transfers (provider regions)
- [ ] Retention: account data until deletion; photo trash 30 days then purge, backup copy +30 days; logs 30 days; billing records per tax law
- [ ] Account deletion & what happens to the shared space (account-deletion.md); export
- [ ] Subscription end: **nothing is deleted and nobody is locked out**; over quota → new uploads blocked until space is freed or the plan is renewed; viewing/downloading continue
- [ ] Partner data: the other member's content stays after one account is deleted
- [ ] Children: not intended for under 18 (couples, intimate photos)
- [ ] Breach notification commitment; user rights (access, correction, deletion, portability, objection)

## 3. Store declarations (draft mapping)

**Google Play — Data safety** (collected, not sold, encrypted in transit: yes, deletion request: yes):
- Personal info: name, email (account management) — required
- Photos: collected, **encrypted end-to-end** (Play allows declaring E2E-encrypted data; confirm current form semantics), app functionality
- User content: other (memories text, comments) — app functionality
- Location: approximate/precise *only if the user types or picks it* for a memory — app functionality, optional
- App info & performance: crash logs (when added), diagnostics
- Device or other IDs: device identifier generated by the app (key binding)
- Financial info: purchase history (via Play Billing)
- No data shared with third parties for advertising; no ads SDK

**Apple — App Privacy**: Contact info (name, email) linked to user; User content (photos — encrypted, other user content) linked; Location (if entered) linked; Identifiers (user id, device id) linked; Purchases linked; Diagnostics (crash data, when added) not linked if possible. Tracking: **No**.

**Age rating**: user-generated private photos between two users, no public sharing → expect 17+ (Apple) / Mature (Play) depending on questionnaire answers; target audience 18+.

**Subscription disclosure** (both stores): price, period, auto-renewal, how to cancel (store settings), free plan contents, restore purchases, links to terms & privacy on the paywall — the Compare plans screen must show them once real billing ships. Refunds are handled by Apple/Google under their policies; state that in the terms.
